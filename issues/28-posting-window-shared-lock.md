# 投稿期間ロックの共有化

## 管理状況

- 状態: **対応済み**（コード変更とPostgreSQL並行統合テスト。採点効果は未計測）
- 対応範囲・完了条件: 同一期間の異なる利用者の投稿を並行可能にし、同一利用者の投稿枠排他と期間切替整合性を保つ。
- 実装コミット/記録: `createPostHandler` の投稿期間行取得を `FOR SHARE` に変更。
- 検証済み/未検証: PostgreSQL統合テストで異なる利用者の並行投稿、同一利用者の同時投稿枠排他、投稿中の期間終了待ち、期間切替後の新期間再検索、削除後2回の上限を確認。全リージョンのベンチ、投稿後フィード到達率、実機への配備、初期化・再起動後の確認は未実施。
- 期待効果: **中（仮説）**。実測効果: **未計測**。
- 関連issue: [14 投稿期間ロック競合](14-posting-window-lock-investigation.md), [18 usersテーブルロック](18-users-table-lock-investigation.md), [10 永続性・再起動](10-durability.md)

## 変更理由

[issue 14](14-posting-window-lock-investigation.md)の2026-10-31 PostgreSQLログ4スナップショットで、投稿期間取得SELECTに対応する1秒以上の待機通知を確認した。最大の取得待ちはスナップショットごとに約2.86〜3.80秒。これは待機時間が記録された根拠だが、ログ収集時の負荷フェーズや配備コード、採点対象活動との相関は未確認であり、得点向上を意味しない。

投稿期間行の更新を防ぐ必要はあるが、同じ期間へ投稿する別利用者間を排他する必要はない。`FOR SHARE` は同じ行の他の共有ロックと共存し、期間終了・切替のUPDATEとは競合する。利用者行の `FOR NO KEY UPDATE` は維持し、同一利用者の投稿枠チェックを引き続き直列化する。

## 制約と受け入れ条件

- 投稿期間の終了・切替は投稿transactionの完了まで待ち、投稿はロックして検証した現行期間に結び付く。
- 同一利用者の同時投稿は一件だけ成功し、削除後の再投稿回数制限を保つ。
- 共有DBを使う全リージョンからのread-after-writeと、投稿失敗時のrollbackを保つ。
- 同じ設定・初期状態・負荷の変更前後比較で、DBロック待ち、投稿成功数、投稿後の友達フィード検証到達率、実現処理件数/負荷を確認する。未確認の性能効果は推定のまま報告する。
- 初期化の完全性と再起動後の永続性を別途確認する。
