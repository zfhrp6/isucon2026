# 投稿・交流の書き込み後応答を短くする

## 採点への寄与

投稿後の友達フィード検証は通常10点、最後の期間20点。投稿受付から検証までの完了率は高配点へ直結する。ログで投稿POSTの地域別 `reqtime` が長く、コードにも同一リージョン内の並行投稿を直列化する区間があるため、優先度は高い。効果：**大（推定）**。ロック待ち時間や実スコアへの因果は未計測。

## 現状

[`createPostHandler`](../webapp/go/post_api.go#L49) はトランザクション内でユーザーのロック、ユーザー取得、投稿期間取得、日次投稿数、画像・投稿INSERT、投稿再取得を逐次実行する。コメントとRealMojiの作成経路もロック・認可・INSERT・作成結果/ユーザー再取得を行う（[`comment_api.go`](../webapp/go/comment_api.go#L30)、[`realmoji_api.go`](../webapp/go/realmoji_api.go#L35)）。

ログ全体（負荷フェーズ限定ではない）で成功した投稿POSTの `reqtime` 平均は、アジア0.727秒（40件）、米州3.918秒（9件）、欧州3.783秒（8件）。標本数が小さく、リージョンや要求順、DB待ち時間の差を分けられないため、遅延の原因は確定していない。

構造上の改善候補は[`post_api.go`](../webapp/go/post_api.go#L107)の投稿期間行 `FOR UPDATE`。そのロックを取った後、画像blob・投稿のINSERTとレスポンス用の再取得を行い、transaction commitまで保持するため、同一地域の別ユーザー投稿もこの区間で直列化される。ログは実際のロック待ちを記録しておらず、この機構が観測遅延の原因だとは断定できない。ログは `.gitignore` 対象でリポジトリに含まれない。

## 改善方針

まずロック待ち時間・ロック保持時間・DB往復別時間を計測し、投稿期間行ロックの範囲を縮められるか評価する。`FOR SHARE` 等の共有ロック、またはロック順の見直しは、期間終了/切替処理との競合を再現する試験後に選ぶ。別途、書き込み後応答に必要な行を `INSERT ... RETURNING` 等で返し、重複照会を減らす。トランザクション境界と競合制御は維持する。

## 制約・リスク

- 投稿枠の二重利用防止、同一利用者の多重投稿防止、投稿期間終了/切替との競合、既存lock order、失敗時ロールバックを維持する。`FOR UPDATE`を安易に除去しない。共有ロック等の採否は並行テストとDB計測後に決める。
- 成功レスポンスにはDB確定後の値を返し、書き込み後すぐ他リージョンから読めること。
- 投稿画像とRealMoji画像は共有DBへ耐久的に保存し、サーバ再起動後も取得可能にする。
- リクエストの重複再送・失敗時の状態を隠す挙動変更を避ける。

## 検証・受け入れ条件

同時投稿・同一利用者の枠競合・期間終了/切替との競合を検証する。書き込み成功後の別リージョン読み取り、再起動後の投稿/画像取得を確認し、ロック待ち/保持時間、API p95、投稿後フィード検証完了率とスコアを比較する。

## 実装状況

- 投稿作成では、ユーザーのロック取得と応答用ユーザー取得を1クエリに統合し、投稿行は `INSERT ... RETURNING` と投稿期間の結合で取得する。投稿期間行の `FOR UPDATE`、ユーザーロック、画像・投稿の同一トランザクションは維持する。応答用SELECTの削減はロック保持区間の処理数を減らすが、待ち時間・保持時間の実測は未実施。
- コメント作成では、既存のユーザーロック順で投稿者と実行者をロックし、実行者のロック取得時に応答用ユーザーも取得する。コメント行は `INSERT ... RETURNING` で取得する。認可判定とそのトランザクション境界は維持する。
- RealMoji置換では、既存の関係ユーザーロック順で実行者のユーザー行も取得し、RealMoji行は `INSERT ... RETURNING` で取得する。画像とRealMojiの保存、置換処理、認可判定を同一トランザクションに保つ。
- 投稿・コメント・RealMojiそれぞれで、応答用ユーザー取得と作成行の再取得を統合し、2往復ずつ減らす。認可判定内の照会や画像保存の往復は対象外。
- 一時PostgreSQL 17へスキーマを投入し、投稿・コメント・RealMojiの変更後INSERT/RETURNING SQLを架空fixtureで実行した。投稿期間の期限と終了状態、NULLの位置情報、コメント・RealMojiのDB生成時刻が結果に含まれることを確認した。
- fixtureのコメントを明示的にROLLBACKし、別接続で該当行が0件であることを確認した。コミットした投稿・コメント・RealMojiとそれぞれの画像は別接続で読み取れた（画像データは各4バイトのfixture）。また、同じユーザー行への `FOR NO KEY UPDATE` が先行トランザクションのCOMMITまで待機することを2接続で確認した。これはユーザー行ロックの直列化確認であり、投稿期間ロックの競合試験ではない。
- PostgreSQLでの限定SQL検証はHTTP/API全体の同時投稿・同一利用者の枠競合・期間終了/切替・関係変更との競合を検証していない。別リージョンからの即時読み取り、再起動後の投稿画像取得、ロック待ち/保持時間、API p95、投稿後フィード検証完了率、スコアの比較も未実施。受け入れにはこれらの並行テスト・耐久性確認・実測が残る。
