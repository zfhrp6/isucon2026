# プロフィール画像更新で観測した502を切り分ける

## 管理状況

- 状態: **調査中**
- 対応範囲・完了条件: 502の発生層と要求結果を相関し、原因を特定する。完了条件は再現経路の説明と仕様を保つ検証。
- 実装コミット/記録: 実装記録なし。
- 検証済み/未検証: 指定時間窓のstatus・reqtime・upstream応答時間と接続エラーを記録。要求単位の相関・原因・再現性は未確認。
- 期待効果: **中（推定）**。実測効果: **未計測**。
- 関連issue: [06 image read](06-image-read.md), [10 durability](10-durability.md)

## 採点への寄与

プロフィール画像の変更・削除は1回3点。指定窓のPUT 49件中5件が502だった。原因が今回の画像更新要求に関係する不具合なら成功を逃す可能性がある。効果：**中（推定）**。このログだけでは原因や再現性を確定できない。

## 現状とログ観測

[`putProfileImageHandler`](../webapp/go/profile_image_api.go#L17) はJPEGとしてリクエストbodyを読み、デコード・寸法検証後、トランザクションで画像を書き込みプロフィール画像IDを更新する。

nginxログ `logs/nginx/20261031T020717Z-nA4kZQ/isu-asia1/{access.ltsv.log,error.log}` のアジア時間窓（2026-10-31 02:06:25–02:07:18 UTC）では、プロフィール画像PUTは49件: 204が2、400が32、403が10、502が5。502の `reqtime` は0.556–0.570秒（平均0.562秒）、`apptime` は全件0.000秒と記録されていた。[nginx設定](../ops/config/nginx/isu-asia1/nginx.conf#L48)では `apptime` は `$upstream_response_time` であり、Go内部の実行時間ではない。同じ時間窓にerror logでconnection reset/broken pipeが6件観測されたが、要求単位での対応は未確認。URL・query・IPなどの値は記載しない。nginxログは `/logs/nginx/` としてGitignoreされ、リポジトリに含まれず、現在の作業領域からも参照できない。

`apptime=0` と約0.56秒の `reqtime` は、Go内部の処理時間やJPEGデコードを原因とする根拠にはならない。`apptime` はnginxからupstreamへの応答時間で、0.000はこのログ指標が記録した値にすぎず、Go内部の処理時間が0だったことを意味しない。nginxとupstreamの接続、要求bodyの送受信、アプリ側での早期終了、クライアント切断などを相関できておらず、502の発生箇所は未確定。400/403も初期検証や不正入力を含み得るため、単独では障害と数えない。

## 改善方針

この時間窓に絞ってnginx error logとGo側ログを時刻・要求識別子（存在する場合）で突合し、upstream接続失敗/リセット、body読取失敗、早期拒否のどこで応答が終わったか調べる。再現環境では正しいJPEG・壊れたJPEG・Content-Type違反・切断を分けて確認し、nginxが返すstatusとGoの処理結果を記録する。まず原因を確定し、再現した経路だけを修正対象にする。

## 制約・リスク

- SecretKey認証、IP ban、画像形式と512x512上限、画像DB保存の耐久性を維持する。
- 400/403を一律に成功へ変えたり、認証・IP制限・検証を緩めたりしない。
- 無効な画像や切断要求に対する既存の外部仕様を維持し、投稿画像等と同じ画像共有・再起動後永続性を保つ。
- ログに秘密情報、IPアドレス、署名付きURLを転記しない。全error.logの件数は過去分が混在するため、指定時間窓の外を今回の原因根拠に使わない。

## 検証・受け入れ条件

有効JPEGのPUTが204で完了し、新画像が全リージョンで直ちに読め、再起動後も取得できる。形式違反・寸法超過・認証不備は従来のstatusを維持する。再現試験のログで502の発生源が特定され、修正後に同じ要求群で5xxが再発しないことを確認する。
