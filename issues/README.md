# Go アプリのスコア改善候補

ここでは、現行の Go 実装と、2026-10-31 の nginx access/error log の集計から見つけた改善候補を整理する。ログは1回分の観測で、APIごとのSQL時間やロック待ちを含まないため、効果は仮説でありボトルネックの断定ではない。

効果は、**大**＝複数の頻出経路または高配点活動の完了率を変える可能性がある、**中**＝対象経路では効くが影響範囲・加点機会が限られる、**小**＝低頻度または単一活動への寄与が中心、と定義する。点数の保証ではない。

## 現在の優先判断

最上位の行動は、実装案を選ぶことではなく、同一条件の走行で得点を取りこぼしている区間を計測・特定すること。利用者・投稿期間単位で、通知受信、投稿成功、直後の画像/投稿詳細取得、期間終了前の友達フィード検証について時刻と成功/失敗を追跡し、途切れる/期限超過する段階を数える。アクセス時間の平均や累積値だけでは採点律速を決めない。得点、投稿後フィード検証の到達率、各段階の成功率、DBクエリ時間・ロック待ち・接続プール待ちを個別に観測する。設定と初期状態を揃えたbaselineと比較し、実現処理件数/負荷も観測記録する。

- **未着手**: 提案段階で、対象を絞った調査・実装記録がない。

## ログ観測の範囲と読み方

集計元はローカルの `logs/nginx/20261031T020717Z-nA4kZQ/{isu-asia1,isu-america1,isu-europe1}/access.ltsv.log` と各 `error.log`。`/logs/nginx/` は `.gitignore` 対象で、ログ自体はこのリポジトリに含まれず、現在の作業領域からも参照できない。以下の値はログが存在した時点の観測記録で、同じ収集物を配置すれば再集計できる。URL・利用者識別子・IP・署名付きクエリは記録しない。

集計時は各ファイル全体（初期検証・異常系を含み、負荷フェーズだけに限定しない）をLTSVとして読み、`method`・queryを除いたURI path・`status` で群分けして `reqtime` 秒を集計した。再集計の読み込みとpath正規化は標準Pythonで次の形にできる。

```python
from pathlib import Path

rows = [
    dict(field.split(":", 1) for field in line.split("\t") if ":" in field)
    for line in Path("access.ltsv.log").read_text().splitlines()
]
for row in rows:
    row["uri"] = row["uri"].split("?", 1)[0]
```

これを3リージョンの各access log全体に適用し、`float(row["reqtime"])` を対象method/path/statusに絞って集計する。平均は対象リクエストの `reqtime` 算術平均。nginxの[`alp_ltsv` log format](../ops/config/nginx/isu-asia1/nginx.conf#L40)では `apptime` を `$upstream_response_time` として記録している。これはupstreamへの通信を含む応答時間で、Go内部の実行時間ではない。`alp` のデフォルト指標は `apptime` なので、以下の `reqtime` 集計根拠にはしていない。`reqtime` の合計は各リクエスト時間の総和で、並行リクエストを含むためCPU時間でも実時間でもない。

集計時に確認したaccess logのSHA-256は、アジア `c5812ace524c7102569fab67bb0a02934ff21903a0b99aaa3802e36db3ef1e74`、米州 `61e27a2bb35b405cdbcb0c0ea630669a6f3786954a1e338b02c9ac3c2918ac90`、欧州 `2ea876ace193d8a1456b835b48b4966585af8a109bb83c0ec961dd68a5eac1b9`。

各access logの全行数はアジア1667、米州147、欧州166。全ファイル中の画像GETでstatusを問わない `reqtime` 合計は297.820秒、通知以外の全リクエストの合計は902.979秒（約33%）。これは負荷フェーズ限定値ではなく、全体の経過時間に対する割合でもない。200応答の画像GETはアジア286件（平均0.612秒、画像ID 240種類）、米州43件（平均1.330秒、43種類）、欧州40件（平均1.261秒、40種類）。同一IDの重複はアジアに46回あり、米州・欧州では観測されなかったため、このログでは欧米の要求時キャッシュのヒット機会を確認できない。将来のヒット可能性を否定するデータではない。

画像200応答をサイズ別に見ると、32KiB以下の平均はアジア0.786秒（202件）、米州1.455秒（36件）、欧州1.342秒（33件）。256KiB超はアジア0.193秒（84件）、米州0.686秒（7件）、欧州0.878秒（7件）。小さい画像の平均が長いが、リージョン・要求順・データ状態がそろった比較ではないため、サイズが原因とは結論しない。

## 先に守る採点・仕様条件

- 配点は[公式マニュアル](../official_resource/manual.md#スコアの計算)を参照。通常期間の投稿後フィード検証は10点、最終期間は20点で、地域倍率はアジア1、欧州・米州1.5。加点対象の上限もあるため、リクエスト数だけを増やす設計は狙わない。
- FAIL の走行は0点で、最後の走行が最終スコアになる。速度と同じ重さで、初期化・権限・永続性の正しさを扱う。
- 仕様変更は禁止。特に書き込み直後の地域をまたぐ読み取り反映、公開範囲・友達・ブロック変更の即時反映、署名付き画像URLの検証、投稿削除後5秒を過ぎた画像の拒否、初期化の完全性を保つ。
- ルーター迂回やリージョン間遅延・帯域制限の回避、DB同期耐久性の緩和、監視・ログ・タイムアウトの削除は改善案に含めない。
- アプリは競技環境で全リージョンから共有DBを利用する。地域キャッシュ等を検討する場合も、即時反映と再起動後の永続性を証明できなければ採用しない。

## 実測での選び方

各候補は設定と初期状態を揃えたbaselineで比較する。総スコアだけでなく、投稿後フィード検証の到達率、活動ごとの成功率、APIのp50/p95、DBクエリ数・時間・行数、ロック待ち、接続プール待ち、エラー・タイムアウトを記録する。実現処理件数/負荷の差も記録して解釈する。平均または累積応答時間だけで優先度を決めず、効果が出た経路と得点差を確認する。スコアが上がってもFAILや整合性違反が出る変更は採用しない。
