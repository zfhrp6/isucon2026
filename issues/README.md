# Go アプリのスコア改善候補

ここでは、現行の Go 実装、2026-10-31のnginx access/error logとPostgreSQLログの集計から見つけた改善候補を整理する。各ログは個別の観測スナップショットで、初期検証と採点負荷の帰属、配備コードとの対応は確認できていない。SQL duration・ロック待ちの記録は一部あるが、API単位の完全な計測ではない。効果は仮説であり、ログだけでボトルネックや得点への因果を断定しない。

効果は、**大**＝複数の頻出経路または高配点活動の完了率を変える可能性がある、**中**＝対象経路では効くが影響範囲・加点機会が限られる、**小**＝低頻度または単一活動への寄与が中心、と定義する。点数の保証ではない。

## スコア改善候補の優先順位

以下は現masterに対する**追加の改善候補順位**。根拠はコード上の処理範囲、観測された待ち、対象活動の配点と、変更・計測の未完了度。スコア改善の実証順位ではない。どの候補も得点差を保証しない。

走行比較の前提として、[24 採点経路計測](24-scoring-path-measurement.md)と[23 デプロイ来歴](23-deployment-provenance.md)を並行して整える。投稿後の通知、投稿、直後の画像/詳細取得、期間終了前の友達フィード検証を利用者・投稿期間ごとに対応付け、実効artifact・設定・DB状態を記録する。比較では同一の初期状態・設定・負荷を揃え、得点、活動成功数、期限内の検証到達率、DB/pool/lock待ち、実現処理量を記録する。これは個別最適化順位とは別の測定前提である。

共通のrun記録、簡単に始められる計測手段、issue別の指標と結果の見せ方は[性能改善候補の計測ガイド](measurement-guide.md)にまとめた。

1. **[14 投稿期間ロック競合](14-posting-window-lock-investigation.md)** — 現masterの投稿作成は共通の投稿期間行を `FOR UPDATE` し、投稿transactionのcommitまで保持するため、同じ地域の異なる利用者の投稿も競合しうる。[05:52:00,05:55:00) UTCの保存ログで100ms以上のduration記録250件、`log_lock_waits` による取得までの待機164件（待機時間合計344.622秒、最大3.926秒）を観測した。ログは累積・複数走行を含み、採点負荷・artifact・得点との因果は未確認。`feat/14` の `f1e07c1` にある `FOR SHARE` 案とDB並行統合テストはmaster未統合で、実機・得点効果も未確認。
2. **[16 認可読み取りスコープ](16-scoped-authorization-reads.md)** — 現行feedは認可候補SQL内で関係を判断する一方、事前に取得するviewer関係情報を候補取得へ渡していない。未統合の`feat/16`ではfriendsがある場合feed前SELECTを5回から2回、friendsがない場合4回から2回に削減する。feed活動のDB処理削減が期待できるが、HTTP認可試験・性能・得点の確認は残る。
3. **[02 閲覧者コンテキスト](02-viewer-context.md)** — 投稿詳細・コメント・RealMoji等で共有される逐次viewer読取をまとめる。未統合の `feat/02` (`47c7a25`) は友達ありで照会を5回から2回、友達なしで4回から2回にする案。複数の読取活動に波及しうる。#16とfeed経路の削減効果を重ねて数えず、残る経路で評価する。
4. **[18 usersロック](18-users-table-lock-investigation.md)** — [05:52:00,05:55:00) UTCの `log_lock_waits` 記録で、users行ロック取得までの待機61件、テーブルロック21件を観測した。これは `deadlock_timeout=1s` を超えた待機の記録で、最大待機はそれぞれ3.880秒、6.024秒。投稿期間ロック待ちからusers行ロックへ波及する仮説もあるため、まず#14適用前後のblockingを分離する。
5. **[07 通知ポーリング](07-notification-polling.md)** — SSE接続ごとに500msごとに利用者と通知の照会を行う。待機接続数に応じてDB仕事量が増え、通知の遅れが高配点の投稿後検証時間を削る可能性がある。実際の同時接続数、DB負荷、通知から投稿までの遅れは未計測なので、相関を確認してから対策する。
6. **[03 セッション索引](03-session-lookup.md) / [26 PostgreSQL索引調査](26-postgresql-index-investigation.md)** — `token_hash`索引がなければ認証必須APIの頻出照会に有効な可能性がある。ただし実DBカタログ、セッション件数、実行時間の最新確認が必要。現DDLだけから索引追加の性能効果は断定しない。
7. **[17 画像署名CPU](17-image-signature-cpu.md)** — 旧実装のCPU profileで高い署名stack寄与を確認し、`69d6365`のHMAC state/buffer再利用は現HEADに統合済み。1,000段の出力は維持する。残る比較は最新実装のCPU/allocs・API・得点で、応答内の重複署名は[34](34-response-image-signature-reuse.md)、捨てる行の加工は[32](32-feed-response-page-limit.md)・[33](33-relationship-response-page-limit.md)・[04](04-user-search.md)・[05](05-interaction-reads.md)へ分ける。旧profileを現在の節約率や画像DB時間と混同しない。
8. **[25 DB接続再利用](25-db-connection-reuse.md)の残る比較** — idle16は採用済み。地域別open上限は現HEADにあるが比較未実施。pool待ちを確認する価値はある一方、接続上限を増やしてもDBロック競合は解消しないため#14/16/02の結果と合わせて判断する。
9. **[04 ユーザー検索](04-user-search.md) / [05 Memories交流取得](05-interaction-reads.md)** — いずれも行数削減の余地はコード上にあるが、取得行数・SQL時間・採点寄与は未計測。#04はUnicode照合契約、#05は投稿ごとの件数・順序を保つ必要があるため、実測してから着手する。
10. **[29 画像本体ローカルキャッシュ](29-image-body-local-cache.md)** — [05:52:00,05:56:00) UTCの累積ログで画像IDの再出現は地域別約12–15%。これは同一走行内のキャッシュhit率ではなく、cold demand-cacheの機会を示すだけ。認可DB照会とcold missのblob転送は残るため、現時点の期待効果は小さい。

現masterの [15 空フィード早期判定](15-empty-feed-short-circuit.md) は、未投稿なら候補SQLを実行せず空応答を返す実装が既にある。残るfeed前関係読み取りは#16で扱う。#01/#09と#06画像索引は記載範囲の実装が統合済みで、#27 JITは比較候補が記録済みのため、新しい未対応改善として重複計上しない。#10/#19/#20は得点改善順位ではなく、初期化・永続性・正しさの受け入れ条件。#12/#22は採点対象の失敗、#11はメモリ制約との関係が確認できた場合に再評価する。

ユーザー報告では、09の応答用DB往復削減を含むコミット `2cbfead`（merge `1fe7f30`）後も目立ったスコア向上はなかった。比較条件と実配備を独立確認できていないため、この報告は改善が無効だった証拠ではない。

[05:52:00,05:55:00) UTCを切り出したロック待ち観測の詳細と制約は[issue 14](14-posting-window-lock-investigation.md)、[issue 18](18-users-table-lock-investigation.md)に記録した。累積ログは複数走行を含むため、異なる時間窓の合計を単一走行の待ちや得点原因として扱わない。

PostgreSQL実機の代表フィードSQLでは、JITを一時的に無効化した単発比較でexecution短縮を観測した。ユーザーからJIT対応後のスコアが約5000点から約7500点へ上がったとの報告もあるが、比較条件とJIT単独の寄与は未確認である。詳細は[JIT比較](27-postgresql-jit-comparison.md)に記録し、設定と初期状態を揃えたベンチ結果から採否を判断する。

## 対応状況

- **未着手**: 提案段階で、対象を絞った調査・実装記録がない。
- **調査中**: ログやコードの根拠はあるが、原因・寄与・完了条件の判断が残る。
- **対応中**: 実装が存在するが、現HEADへの統合や記載範囲の完了が確認できない。
- **対応済み**: issueに記した実装範囲が統合済み。全シナリオ検証や性能・得点改善の実証を含意しない。

## ログ観測の範囲と読み方

以下は別時刻のスナップショットであり、母集団を混ぜない。過去の `020717` 集計は歴史的記録として下記に残す。新しい `030854` 集計は全ファイル集計で、初期検証・異常系が混在する可能性がある。ログは `.gitignore` 対象でリポジトリに含まれない。URL・利用者識別子・IP・署名付きクエリは記録しない。

集計時は各ファイル全体（初期検証・異常系を含み、負荷フェーズだけに限定しない）をLTSVとして読み、`method`・queryを除いたURI path・`status` で群分けして `reqtime` 秒を集計した。再集計の読み込みとpath正規化は標準Pythonで次の形にできる。

```python
from pathlib import Path

rows = [
    dict(field.split(":", 1) for field in line.split("\t") if ":" in field)
    for line in Path("access.ltsv.log").read_text().splitlines()
]
for row in rows:
    row["uri"] = row["uri"].split("?", 1)[0]
```

## 先に守る採点・仕様条件

- 配点は[公式マニュアル](../official_resource/manual.md#スコアの計算)を参照。通常期間の投稿後フィード検証は10点、最終期間は20点で、地域倍率はアジア1、欧州・米州1.5。加点対象の上限もあるため、リクエスト数だけを増やす設計は狙わない。
- FAIL の走行は0点で、最後の走行が最終スコアになる。速度と同じ重さで、初期化・権限・永続性の正しさを扱う。
- 仕様変更は禁止。特に書き込み直後の地域をまたぐ読み取り反映、公開範囲・友達・ブロック変更の即時反映、署名付き画像URLの検証、投稿削除後5秒を過ぎた画像の拒否、初期化の完全性を保つ。
- ルーター迂回やリージョン間遅延・帯域制限の回避、DB同期耐久性の緩和、監視・ログ・タイムアウトの削除は改善案に含めない。
- アプリは競技環境で全リージョンから共有DBを利用する。地域キャッシュ等を検討する場合も、即時反映と再起動後の永続性を証明できなければ採用しない。

## 実測での選び方

各候補は設定と初期状態を揃えたbaselineで比較する。総スコアだけでなく、投稿後フィード検証の到達率、活動ごとの成功率、APIのp50/p95、DBクエリ数・時間・行数、ロック待ち、接続プール待ち、エラー・タイムアウトを記録する。実現処理件数/負荷の差も記録して解釈する。平均または累積応答時間だけで優先度を決めず、効果が出た経路と得点差を確認する。スコアが上がってもFAILや整合性違反が出る変更は採用しない。
